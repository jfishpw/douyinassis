# 故障排查（troubleshooting）

## 1. 欢迎/发送失效：话术发不出、欢迎不触发

**最可能原因：抖音改版，DOM 选择器失效。**

当前依赖的选择器（`run_loop.py`）：

| 用途 | 选择器 | 位置 |
|------|--------|------|
| 评论输入框 | `[data-slate-editor=true]` | `send_comment()` |
| 发送按钮 | `[data-e2e="live-chatting"] ~ *` | `send_comment()` |
| 进入直播间消息 | `div.webcast-chatroom___bottom_message` | `fetch_new_arrivals()` |
| 消息里的用户名 | `span.v8LY0gZF` | `fetch_new_arrivals()` |

**重新定位方法：**

1. Chrome 打开直播间 → F12 开 DevTools → 左上角箭头工具点选评论框
2. 看 Elements 面板里对应节点的 class / data 属性
3. 用 `python cdp_client.py list` 确认 CDP 在线，再改 `run_loop.py` 里对应选择器
4. 改完重启 `start.ps1`

注意：抖音的 class 名（如 `v8LY0gZF`）是构建产物，改版就会变；`data-e2e` 属性相对稳定，优先按它找。

## 1.6 日志刷 `SyntaxError: missing ) after argument list`，启动后完全不互动

- **现象**：`loop.log` 每 10~60 秒重复出现 `连接失败: {... 'className': 'SyntaxError', 'description': 'SyntaxError: missing ) after argument list' ...}`，永远起不来，不欢迎、不点赞、不发话术。
- **原因**：`wait_ready()` 里探测评论框/发送按钮的 JS 选择器字符串**引号写坏**（少一个 `"` 或 `'`），JS 直接解析失败。改代码时的高频错误。
- **定位**：看 `run_loop.py` 里 `btn = client.eval(...)` 那行，正确写法必须是：

  ```python
  btn = client.eval("!!document.querySelector('[data-e2e=\"live-chatting\"] ~ *')")
  ```

  注意结尾是 `live-chatting"] ~ *`，**`"]` 不能少**。同理 `send_comment()` 里的发送按钮选择器。
- **修复**：改对引号后重启脚本。若不确定，先用 CDP 直接 eval 该表达式验证能否返回 `true`。

## 1.7 一直 `评论框 -- 发送按钮 --`，主播未开播

- **现象**：日志连续 6 次 `评论框 -- 发送按钮 --`（0s~50s），伴随 `页面实况: {... 'text': '... 直播加载中' ...}`，60 秒后提示「评论框 60s 内未出现」，然后按退避重连，循环往复。
- **原因**：**主播没开播**。抖音直播间此时只渲染一个"直播加载中"的空壳页面，评论框和发送按钮根本不存在，任何选择器都找不到——不是脚本问题。
- **确认方式**：看日志那行 `页面实况`：`video` 通常仍是 1（播放器容器在），但 `chat` 为 0、`text` 含「直播加载中」。
- **处理**：等主播开播即可。脚本每轮检测失败后会 `Page.reload` 刷新一次页面，开播后会自动重新加载、进入就绪，**无需手动重启**。若开了几轮仍不就绪，手动点一下浏览器刷新再观察。
- **注意**：别用 `document.cookie` 判断是否登录——抖音的 `sessionid` 是 HttpOnly，JS 读不到，会误报"未登录"。要确认登录状态，用 CDP 的 `Network.getCookies` 或直接看页面右上角头像。

## 1.8 多行话术导致促销每 30 秒重试、发不出去（`SyntaxError: Invalid or unexpected token`）

- **现象**：话术里加了一行（或多行）后，日志变成
  `[促销 #14] 失败: {... 'className': 'SyntaxError', 'description': 'SyntaxError: Invalid or unexpected token' ...}，30s 后重试`，
  每 30 秒重复一次，永远发不出去；欢迎文案带换行时同理（两者共用 `send_comment`）。
- **原因**：`send_comment` 把话术拼进 JS 单引号字面量，旧实现只转义了 `\` 和 `'`，**没有处理换行**。换行会让 JS 字符串提前断开，整条表达式解析失败。
- **修复写法**（当前版本已内置）：用 `json.dumps` 生成 JS 字面量，换行/引号/反斜杠全部安全：

  ```python
  def js_str(s):
      return (json.dumps(s, ensure_ascii=False)
              .replace('\u2028', '\\u2028').replace('\u2029', '\\u2029'))
  # 使用：document.execCommand('insertText', false, {js_str(text)})
  ```

  验证方法：拿生成的表达式喂给 JS 引擎（`node -e "new Function(源码)"`）能通过即语法正确；
  再把字面量求值与原文比对，确认字符没有丢失。
- **现行策略**：促销话术**支持多行**（2026-11-05 起，每行一条，按 `promo.mode` 顺序或随机发送），但**发送时仍是逐条单行**——`send_comment()` 会把行内换行压成空格，所以不会重现上面那个语法错误。欢迎语仍**强制单行**（要和 `@用户名` 拼成一行）。面板里的多行只用于「分行列话术」，不是把多行拼成一条发出去。

## 2. 点赞无反应

抖音网页版点赞规则：**按住 Z 不放持续点赞，松开才停；单击无效；计数有 1-2 秒延迟**。按可能性排序：

1. **播放器未激活**：快捷键监听器挂在播放器上。代码每轮点赞前会 JS focus 播放器；若 `[data-e2e="living-container"]` 选择器失效，激活会静默失败，点赞全无。用 DevTools 确认该选择器仍有效。
2. **按成了单击 / 没补自动重复**：确认实现是 keyDown → 每 0.4 秒补发 autoRepeat keydown → keyUp 的完整"长按"语义，且 keyDown 带了 `text` 参数。
3. **焦点在评论框**：正常逻辑会先 blur，但若评论框选择器已失效，blur 会静默失败，Z 就打进输入框了——表现为输入框里出现字母 z。
4. **页面没激活**：把抖音直播间窗口切到前台再观察（探针可查 `document.hasFocus()`）。
5. **快捷键变了**：确认当前抖音 PC 网页版点赞快捷键仍是 Z。
6. **点赞频率限制**：实测约 1-2 秒 1 个赞，`like.hold` 调得再长也不会更快，属抖音限流。

**验证点赞是否生效**：看 `loop.log` 里 `[点赞] 第 N 轮` 是否递增；直播间信息栏"本场点赞"计数是否增长（有延迟，等 2-3 秒再看）。

## 3. CDP 连接中断（WinError 10053 / socket is already closed）

- Chrome 被完全关闭、直播间页面崩溃、或 Chrome 重启都会导致。
- **2026-10 起脚本已支持自动重连**：日志出现 `CDP 连接断开` → `10s 后重连` 是正常流程，Chrome 恢复后自动继续，无需手动重启。
- 若重连一直失败：确认 Chrome 是以 `--remote-debugging-port=9222` 启动的（start.ps1 已处理；手动开的 Chrome 没带调试端口就连不上）。
- 抖音页面被关掉时，脚本会按 `live_url` 自动重新打开。

## 3.5 同一个人被重复欢迎 / 话术发重

- **多个 run_loop.py 实例在跑**：每个实例有独立的已欢迎列表，会互相重复欢迎、抢评论框。脚本有单实例锁（第二个实例启动即退出），`start.ps1` 也不会重复拉起。
- 排查：看 `loop.log` 里有没有多个"配置加载完成"会话标记，就是多次启动留下的。用 `stop.ps1` 停掉再 `start.ps1` 启动一个。

## 3.7 stop.ps1 会不会误杀其他进程

**不会，且这是设计红线**：stop.ps1 只做两件事——读锁文件 `run_loop.lock`（PID + mtime 心跳）、创建 `run_loop.stop` 信号文件等实例自行退出。它**不扫描进程列表、不调用 Stop-Process**。

历史教训（2026-10-24）：早期版本按"命令行包含 run_loop.py"匹配进程，而 Windows 上 AI 助手（hermes）的命令执行层会产生命令行里带 `run_loop.py` 字样的 python 包装进程，导致误杀助手进程。任何改动都不要把进程匹配加回来。

## 3.8 实例卡死 / stop.ps1 说"没在运行"但其实在跑

- **2026-10-31 实际事故**：锁文件被外部删成 0 字节后，旧版 stop.ps1 判定"没有在运行中的实例"，实例却继续跑了 6 天。现在 stop.ps1 改为**信号文件握手**：创建 `run_loop.stop`，看它是否被实例消费掉，因此不依赖锁里的 PID。
- 现在若真遇到卡死（15 秒内信号未被消费且锁里 PID 活着），才会提示"可能已卡死"——确认 PID 对应的是 run_loop 实例后，手动在任务管理器结束该 python 进程。
- 若 stop.ps1 提示"没有检测到运行中的实例"但你确定有：等 10 秒再执行一次（实例可能正处在最长 60 秒的退避等待里，信号每 1 秒检查一次）。

## 3.6 欢迎时好时坏（随机漏欢迎）

- `welcome.history` 太小：直播间刷屏快时，"来了"消息会滚出回看窗口。调到 200 以上。
- 早期版本 CDP 命令未串行，三个循环共用一个连接会互相吞响应导致随机超时——2026-10 已修复（send 加锁）。若还在用旧版 run_loop.py，更新它。

## 3.9 控制面板打不开 / 设置不生效

- **打不开**：先看 `loop.log` 有没有 `[面板] 控制面板已启动: http://127.0.0.1:xxxx`。端口被占用时会自动顺延（8765→8774），日志里写的是实际地址。
- 端口全被占用 → 日志出现 `[面板] 启动失败`：改 `config.json` 的 `panel.port` 后重启脚本。
- `panel.enabled=false` 时面板不启动，属预期。
- **设置保存后没生效**：除 `panel.port` 和 `live_url`（下次重连才用）外，其余参数都是热生效的，1~3 秒内起效；若感觉没变，看日志有没有 `[控制] 配置已保存并生效`。
- **手改 config.json 没生效**：脚本会自动重载（面板轮询 2 秒、连接中每 10 秒、断线重试每 1 秒检查一次），日志应出现 `[控制] 检测到 config.json 被外部修改，已重新加载`。若日志报 `解析失败` 或 `内容有误`，说明 JSON 写坏了或超范围，此时**保留当前配置继续跑**，改对即可。
- **只暂停某一个功能**：三个开关互相独立，`POST /api/control {"like": false}` 只改点赞，其他不变；`{"all": false}` 才是全部暂停。
- **切换开关没反应**：确认面板顶部显示"已连接直播间"；未连接时切换会写盘但不会立刻有动作，连上后按新配置执行。
- 面板页 500：`panel.html` 不在 `run_loop.py` 同目录，或文件名不对。

## 4. start.ps1 双击没反应 / 一闪而过

- PowerShell 执行策略限制：右键 start.ps1 → "使用 PowerShell 运行"；或先执行 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`。
- 看报错信息判断，常见就是 CDP 失败或 python 不在 PATH。

## 5. 欢迎了同一个人多次

- `welcomed.json` 每次启动会清空（设计如此：新 session 重新欢迎）。
- 单次运行内重复欢迎：检查 `fetch_new_arrivals()` 的 `welcome.history` 是否太小，漏看了更早的消息。

## 6. 话术发送成功但直播间看不到

- 抖音对相同内容短时间重复发送会折叠/去重；适当调整 `promo.interval` 和文案。

## 7. 实际间隔和设定值不一样 / 想设得更快

**不是 bug，是设计如此**：

- **随机化**：所有间隔会在设定值上下按 `jitter.ratio` 浮动（默认 ±10%）。设定 200 秒，实际 180~220 秒随机。日志里 `[促销] 下一条约 214s 后（基准 236s）` 就是当次抽到的真实间隔。不想要就关掉 `jitter.enabled`（面板「节奏随机化」区块），或把比例设为 0。
- **最快限制（频率下限）**：每个间隔都有最小值，**输入小于它的值会被校验拒绝**，浮动结果也不会低于它。当前的下限是：发送间隔 10 秒、检测频率 1 秒、两条欢迎间隔 0 秒、点赞间隔 1 秒、按住时长 0.3 秒；上限分别是 3600 / 60 / 120 / 300 / 60。
- 这些数字定义在 `run_loop.py` 的 `LIMITS` 里，是唯一真源——校验提示、面板上每个输入框后面的实时范围提示（`允许 10~3600 秒，最快 10 秒；当前实际 212~260 秒`）都读它。要调整限制只改这一处。
- **按住时长不参与随机化**：它是单轮点赞持续的时长，不是间隔。

## 8. 双击 start.ps1 后浏览器没打开 / 提示"CDP 失败"

**先看是不是这个坑**：窗口里显示 `Chrome 已在运行`，紧接着 `CDP 失败`。

- **原因**：判断"Chrome 是否在运行"如果按**进程名**（`Get-Process chrome`），会把其他也叫 `chrome.exe` 的进程一起算进去——典型是 **WorkBuddy 自带的 chromium**（路径 `...\hermes\tools\chromium-*\chrome-win64\chrome.exe`）。脚本于是以为 Chrome 开着、跳过启动，可那些进程并没有 `--remote-debugging-port=9222` 参数，CDP 自然连不上（2026-11-02 实际踩到）。
- **现行实现**（start.ps1 第 2 步）：不再写死安装路径，按顺序探测 `browser.chrome_path`（config）→ 注册表 `App Paths\chrome.exe`（HKLM/HKCU）→ `Program Files` / `Program Files (x86)` / `%LOCALAPPDATA%` 用户级安装 → 都找不到就回退 Edge；判断"是否已在运行"用 `ExecutablePath` **全等**比较（与探测到的那个 exe 比），不受同名进程干扰；启动前**先探测 9222 端口**，通了直接复用，不通才启动，启动后最多等 15 秒轮询。
- **换电脑后目录不一样**是最常见的失效原因：如果新机器的 Chrome 装在自定义位置（绿色版、非 C 盘、便携版），脚本探测不到时会在 config.json 里加一行即可：
  `"browser": { "chrome_path": "D:\\ChromePortable\\chrome.exe" }`
  配置目录同理，用 `browser.user_data_dir` 指定；留空时脚本会取 `%LOCALAPPDATA%\Google\Chrome\User Data` 作默认值并**显式传** `--user-data-dir`。⚠️ **不能省掉这个参数**：Chrome M136+ 起，传了默认目录或不传但用默认目录时，`--remote-debugging-port` 会被**静默忽略**，现象就是"浏览器正常打开、但 9222 连不上、脚本报 CDP 失败"。
- **仍然失败时**手动启动一次，把真实报错暴露出来：在 PowerShell 里执行探测到的 exe 路径 + 参数 `--remote-debugging-port=9222 --remote-allow-origins=*`（用 `& '路径'` 调用）。随后浏览器访问 `http://127.0.0.1:9222/json/version`，应返回含 `"Browser": "Chrome/..."` 的 JSON。
- **判断 Chrome 到底关没关**：别看任务管理器的 `chrome.exe` 数量（会把别的 chromium 算进去），看两样——可执行文件路径是否在 `Program Files\Google\Chrome` 下、`http://127.0.0.1:9222` 是否有响应。
- 若确实有真实 Chrome 在跑但没开调试端口，脚本会提示"请先完全退出 Chrome"——**同一个配置目录无法再以调试模式启动第二个实例**。

## 9. 编码复读不工作（识别不到 / 不发公屏）

按可能性排序：

1. **没开 Windows 实时辅助字幕**：设置 → 辅助功能 → 字幕 → 打开"实时辅助字幕"，或按 `Win+Ctrl+L`。脚本读的是这个窗口，日志会提示"没找到 Windows 实时辅助字幕窗口"。Chrome 自带的"实时字幕"是另一个窗口，也能读但延迟更大，不推荐。
2. **没装 `uiautomation`**：`pip install uiautomation`。没装时日志只有一行 `[复读] 未安装 uiautomation…`，其余功能不受影响。
3. **主播没说到带锚点的编码**：提取要求"编码/款号/编号/货号/链接/小黄车"附近出现 2~6 位数字；只说"一百零六"不带锚点不会触发（这是刻意的，避免把价格当编码）。
4. **被闸门挡住**：同码冷却（默认 30 秒）、同码次数（默认 2 次）、每分钟上限（默认 2 条）。日志里不会报错，直接跳过；把 `cooldown`/`per_minute` 调大即可观察。
5. **发送失败**：与促销/欢迎共用评论框，若同时抢发会排队（`send_lock`），日志出现 `[复读] 发送失败` 时看 `brief_error` 提示。

**验证方法**：让主播说一句"编码 106"，日志应出现 `[复读] 106 → 已发公屏「编码 106」`，面板"复读次数"加 1、"最近编码"变成 106。

### 9.1 开启/恢复后补发了"以前的编码"，当前说的反而不发（v1.3.2 已修）

- **现象**：功能是中途才在面板开启的（或暂停过一段时间再恢复），结果公屏刷出几条**开启之前**说过的编码，紧接着当前正在说的编码却不发。
- **根因**：`CaptionsTextBlock` 的文本是**整场累积**的一大串，不是"当前一句"。旧实现在功能关闭时把游标 `processed` 重置为 0，重新开启时整段历史都成了"新增内容"，于是①补发历史编码 ②这些历史编码把每分钟配额（默认 2 条）和同码次数（默认 2 次）吃光，轮到新编码时被闸门挡住。
- **修法**：进入启用状态时**先取基线**（`processed = len(当前文本)`），只处理此后新增的内容；文本被清空/变短时同样只从新内容算起。日志会打印 `[复读] 开始监听字幕（跳过已有 N 字历史，不补发旧编码）`，看到这行说明基线已建立。
- **如果你在旧版本遇到**：升级后重启即可；不需要清什么文件。历史编码的计数只存在内存里，重启清零。
